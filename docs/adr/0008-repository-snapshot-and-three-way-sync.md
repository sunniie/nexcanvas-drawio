# ADR 0008: Version repository snapshots and reconcile semantics three ways

- Status: accepted
- Date: 2026-09-10

## Context

Revision-pinned evidence proves what an existing diagram describes, but it does
not explain how that diagram should change after the repository advances. A full
regeneration would discard manual labels, annotations, positions, connector
lanes, and other presentation work. Comparing only the old and new repositories
would also mistake a deliberate user edit for analyzer output.

## Decision

NexCanvas introduces repository snapshot schema `1.0` and semantic sync-plan
schema `1.0` as public-preview contracts.

`nexcanvas analyze snapshot` reads Git-tracked Python, TypeScript, JavaScript,
TSX, JSX, and declaration files from a pinned commit. The first analyzer release
extracts modules, public top-level symbols, and resolvable internal imports. It
does not infer runtime behavior, framework ownership, deployment topology, or
dynamic imports that are not statically provable. Analyzer diagnostics remain in
the snapshot instead of being converted into invented semantic facts.

Every analyzer-managed semantic record carries a stable ID and a
`repositorySync` extension. When a previous snapshot is supplied, Git rename
detection preserves the prior module ID across a file move. Repository facts use
exact file, line, blob, origin, and revision evidence.

`nexcanvas analyze diff` compares two repository snapshots by stable semantic
ID. `nexcanvas sync <project> --repo-root <repository> --dry-run` creates a plan
without modifying the project. `--apply` performs a field-level three-way merge:

1. the last applied repository snapshot is the baseline;
2. a fresh repository snapshot is the incoming source state;
3. the current Diagram Model V3 is the user-edited state.

Source-only changes are applied. User-only changes are preserved. If source and
user changed the same field differently, the current user value wins and the
conflict is reported. Existing presentation records are never regenerated by
sync. Added semantic records receive minimal presentation records; removed
records lose presentation only after their semantic removal is explicitly
confirmed.

Removal is conservative. A removed or analyzer-ambiguous entity, relationship,
or group remains in the model unless its semantic ID is passed with
`--confirm-removal`. Analyzer ambiguity is always surfaced in the plan. Applying
safe additions and updates may therefore finish with retained conflicts or
pending removals, which are represented explicitly in the machine-readable
result.

After an applied sync, NexCanvas updates the analyzer-owned repository source and
facts in `source_model.json`, refreshes `diagram_lock.json.sourceHash`, stores the
new baseline at `repository_snapshot.json`, and writes
`reports/semantic_sync.json`. The normal generation pipeline remains responsible
for invalidating and rebuilding downstream artifacts.

## Public-contract impact

- Adds `repository_snapshot.json` schema `1.0` and semantic sync-plan schema
  `1.0`.
- Adds `analyze snapshot`, `analyze diff`, and the top-level `sync` command.
- Adds contract validation kinds `repository-snapshot` and `sync-plan`.
- Requires Diagram Model V3 for incremental sync; V2 remains readable but must be
  migrated before synchronization.
- Does not change Diagram Model `3.0`, Source Model `2.0`, Diagram Lock `2.0`,
  asset-manifest `2.0`, or pipeline-state `1.0`.

## Consequences

Repository evolution can update confirmed analyzer-managed semantics without
destroying manual layout work. Initial analysis is intentionally conservative
and language-limited. A diagram still needs an agent or human to choose the
appropriate viewpoint and decide whether newly discovered modules belong in the
communicated architecture.
